# Shopify app development

This app is scaffolded from a Shopify app template. See the README for framework-specific details.

Use the [Shopify AI Toolkit](https://shopify.dev/docs/apps/build/ai-toolkit) for all Shopify API and platform work. If missing, install it in the agent host per that page (or `npx skills add Shopify/shopify-ai-toolkit --list` for skill-compatible hosts) — do not add tooling to this repo.

## What this app does

`hikyaku-connect` lets a merchant connect their store to a [Hikyaku](https://hikyaku.org) account, then forwards every paid order to `hikyaku-api` as a delivery job. Two credential flows exist side by side and shouldn't be confused:

- **Shopify OAuth** (`authenticate.admin` / `authenticate.webhook`, via `@shopify/shopify-app-react-router`) — the app's own install/session flow. Sessions live in the `Session` Prisma model, stored by `VaultSessionStorage` (`app/lib/vault-session-storage.server.ts`, in place of the template's `PrismaSessionStorage`): the access and refresh tokens are Vault secrets like the Hikyaku ones, and the row holds only their UUIDs. Delete sessions through it (or `deleteShopSessions`), never with `db.session.delete*`, or their secrets are orphaned.
- **Hikyaku OAuth** (`app/lib/hikyaku-oauth.server.ts`) — a separate PKCE flow against [Hikyaku's Supabase OAuth server](https://supabase.com/docs/guides/auth/oauth-server), started from `app/routes/app._index.tsx` (opens a new tab — the consent screen at `hikyaku/app/oauth/consent` can't render inside the Shopify admin iframe) and completed at `app/routes/hikyaku.callback.tsx`. Tokens are stored as Supabase Vault secrets (`app/lib/vault.server.ts`) — `HikyakuConnection` holds only the vault secret UUIDs — in the `shopify` Postgres schema of the same Supabase project `hikyaku-api` uses. At runtime the app connects as the `hikyaku_shopify` role (`prisma/migrations/20260928000000_least_privilege_role`): read/write on the `shopify` tables only, and Vault only through the `shopify.create_secret`/`read_secret`/`update_secret`/`delete_secret` wrappers, which touch only secrets tagged `hikyaku-shopify`. Migrations run as the privileged role via `DIRECT_URL`, from a developer machine (`pnpm prisma migrate deploy`), never in the Vercel build: `DIRECT_URL` isn't set on Vercel. Prisma is v7: the CLI reads `DIRECT_URL` from `prisma.config.ts` (it loads `.env` itself), the client is generated into `app/generated/prisma` (gitignored; `build` and `typecheck` run `prisma generate`) and imported from there, not `@prisma/client`, and the app connects with `DATABASE_URL` through the pg driver adapter in `app/db.server.ts`, which maps the URL's `connection_limit` and TLS defaults onto node-postgres. Functions run in Vercel's `syd1` region (`vercel.json`), next to the database in `ap-southeast-2`: a session refresh takes several round trips, and from the default `iad1` each one crossed the Pacific.

## Screens

Embedded admin routes under `app/routes/app.*`, built with Polaris web components (`s-*`). React is 18, so prefer form submission over `onChange` on `s-*` fields, and set a boolean attribute by spreading it in only when true (`{...(x ? { selected: true } : {})}`): React 18 writes `false` as the string `"false"`.

- `app._index.tsx` (Home): connect Hikyaku, pick the organisation, then the Connected card. Picking the organisation goes straight on to Locations (`?setup=1`), whose first Save goes on to Orders. While connected, a banner counts active, online fulfilling locations that are unmapped in Hikyaku (or not stored there yet): "N locations aren't mapped. Orders shipped from them will need attention in Hikyaku." A second banner counts the earlier orders Hikyaku lacks (see Orders) and links to Orders.
- `app.locations.tsx` (Locations, also in the app nav and linked from the Connected card): one row per location with `isActive && fulfillsOnlineOrders`, the rest (inactive, or not fulfilling online orders) in a collapsed "Other locations" section. Each row has a picker of the organisation's warehouses plus "Not delivered by Hikyaku". The form component is `app/components/location-mapping-form.tsx`.

- `app.orders.tsx` (Orders, also in the app nav and on the Connected card): HIK-205. orders/paid fires once, so orders paid before the store was connected (or while it was disconnected) never reached Hikyaku. The screen lists the shop's open, paid orders still to ship, newest first, 50 a page (`importableOrdersSearch` in `app/lib/order-import.ts`; Shopify shows apps only the last 60 days without `read_all_orders`), each with a checkbox and a "select all" for the page. Orders Hikyaku already has an `order.paid` event for (`fetchOrderEvents`) are badged "In Hikyaku" or "Needs attention in Hikyaku" and can't be picked. "Add N orders to Hikyaku" runs `importOrders` (`app/lib/order-import.server.ts`): for each picked order it reads the order (`getOrder`) and its fulfillment orders, maps it to the orders/paid payload shape (`orderPaidPayloadFromOrder`, pure and unit tested; line item weights come from the fulfillment orders) and sends it through `buildOrderPaidEvent`/`postOrderEvent` exactly as the webhook would, with the same fulfillment group rules. The Idempotency-Key is `import:<order GID>`, so importing an order twice records it once; an order the webhook already sent would only have its packages linked again, not duplicated. Each order gets an outcome on screen: sent, skipped (cancelled, archived, unpaid or nothing left to deliver since the list loaded) or failed with the reason. If Hikyaku can't list its events (the account lacks `packages.view`), every order is pickable and a warning says so. The `s-checkbox`es are wired to the DOM in `useOrderSelection` (React 18 can't listen to their change event) and the form data is built from them on submit. The Home banner checks the newest 50 such orders paid before `HikyakuConnection.createdAt`.

**Suggestions** (`app/lib/location-mapping.ts`, pure and unit tested): for an unmapped active location, the nearest warehouse in the same country within 5 km (haversine) of the location's latitude/longitude is preselected and badged "Suggested". No coordinates, no country code or no warehouse in range means no suggestion. Loading the screen never saves a suggestion; pressing Save does, as it saves what the pickers show. Warehouses carry a country name ("Australia") and locations an ISO code ("AU"): names are resolved with `Intl.DisplayNames` English region names plus a short alias list (`countryCodeForName`); an unrecognised name never matches.

**Sync.** Every load of Locations re-lists the shop's locations from the Admin API and upserts them all without `mode` and with `mark_missing_stale: true`: new ones arrive `unmapped`, names, countries and street addresses refresh, mappings stay, and locations gone from Shopify are marked stale in Hikyaku. Save sends only the locations whose picker changed, with an explicit `mode`. The `locations/*` webhooks upsert the one location the same way (no `mode`, no `mark_missing_stale`).

**Read-only.** The sync needs `integrations.locations.write`; reading warehouses and mappings only needs `warehouse.view`. The API can't report the caller's permissions, so the sync doubles as the check: when it returns 403, Locations reads `GET /api/v1/integrations/locations` instead and shows the same rows with the pickers and Save disabled and a "View only" banner naming the connected account. The Home banner only reads, so it works for these accounts too.

## Outside the admin

The Shopify admin always opens the app URL with a `shop` param. Without one, `/` (`app/routes/_index/route.tsx`) redirects to Hikyaku's page about the app, `MARKETING_URL` in `app/lib/marketing.ts` (`https://www.hikyaku.org/plugins/shopify`, a Payload page in `hikyaku-landing`). So does `/auth/login`, unless `login()` redirects to an install, which a valid `?shop=` does: that's how Hikyaku's Connected Apps starts one. The template's shop-domain form is gone and shouldn't come back: App Store requirement 2.3.1 forbids asking for the shop domain.

## Hikyaku API usage

All in `app/lib/hikyaku-api.server.ts`, with the shop's Hikyaku bearer token and `X-Organisation-Slug`. Location calls send `platform: "shopify"` and the shop's myshopify domain as `shop_domain`, and each location's street address (`address`): a carrier service callback names its origin only by address, so hikyaku-api matches it against these to find the location's warehouse.

| Call | Function | Used by |
| --- | --- | --- |
| `GET /api/v1/organisations/me` | `fetchOrganisations` | Home, picking the organisation |
| `POST /api/v1/integrations/orders` | `postOrderEvent` | `orders/paid` (`order.paid`) and `fulfillment_orders/*` (`order.fulfillment_updated`) webhooks, Orders (`order.paid` for earlier orders) |
| `GET /api/v1/integrations/orders?platform=shopify&external_order_ids=…` | `fetchOrderEvents` | Orders and the Home banner: which orders Hikyaku already has (needs `packages.view`, at most 100 ids) |
| `GET /api/v1/warehouses` | `fetchWarehouses` | Locations (pickers, suggestions) |
| `GET /api/v1/integrations/locations` | `fetchIntegrationLocations` | Home (unmapped banner) |
| `PUT /api/v1/integrations/locations` | `upsertIntegrationLocations` | Locations (sync on load, Save), `locations/*` webhooks |
| `GET`/`PUT`/`DELETE /api/v1/integrations/shipping-rates` | `fetchShippingRates`, `saveShippingRates`, `deleteShippingRates` | Rate settings (enabled, services, path, shop currency, band settings) with the catalog priced in the shop currency; `applyRates` keeps the path and currency current (GET needs `warehouse.view`, PUT/DELETE `integrations.shipping_rates.write`; a 422 carries `code` and `service_ids`, a 409 means another organisation holds the shop) |
| `GET /api/v1/integrations/shipping-rates/static-plan?platform=shopify&shop_domain=…` | `fetchStaticPlan` | Static rates sync (needs `warehouse.view`) |

## Order flow

`app/routes/webhooks.orders.paid.tsx` is the integration's core: HMAC-verified via `authenticate.webhook`, transformed by the pure function `app/lib/order-event.server.ts`, and POSTed to `hikyaku-api` by `app/lib/hikyaku-api.server.ts`. The webhook handler's response status is a deliberate retry contract with Shopify (500 = retry, 200 = don't).

**Fulfillment groups.** Before building the event, the handler reads the order's fulfillment orders (`getOrderFulfillmentOrders`, 1 s timeout: the POST gets 4 of Shopify's 5 s) and maps them with the pure `app/lib/fulfillment-groups.ts` into `fulfillment_groups`: one group per fulfillment order with its assigned location, delivery method (`SHIPPING`/`LOCAL`/`PICK_UP` become `shipping`/`local`/`pickup`, anything else `none`), the units still to fulfill (`remainingQuantity`) per line item, and a weight in grams (null if any line has no weight). A group's `line_item_id` is the numeric id taken off the `LineItem` GID, the same string as `order.line_items[].id`. An order is never sent without groups, since Hikyaku would then dispatch all of it from the nearest warehouse:

- Admin API error, timeout, or the order not found: 500 (retry).
- Routing not settled: no fulfillment orders yet, a deliverable one with no location (deleted), or an unknown status: 500 (retry).
- `OPEN`, `IN_PROGRESS` and `ON_HOLD` become groups. `CLOSED`, `CANCELLED`, `INCOMPLETE` and `SCHEDULED` (a later delivery, such as a prepaid subscription's next box) are left out; if nothing is left, the order isn't sent (200).
- Line items the payload doesn't list are left out of the groups and logged, since the API rejects the whole event otherwise.

**Hikyaku rates at checkout** (HIK-206/HIK-212). When the shop has Hikyaku rates on (`ShippingRates.enabled`, read by `rateForwarding` in `app/lib/shipping-rates.server.ts`), `orders/paid` sends only orders whose shipping lines include a Hikyaku rate, and skips the rest (200, logged) before reading Shopify. The pure `findHikyakuShippingLine` (`app/lib/hikyaku-shipping-line.ts`) recognises one: a live rate by its `code`, which is the carrier service's `service_code` (`hikyaku:<service_id>`), a static rate by the method definition name the app wrote it under (mapped back to its rate code, `hikyaku:<service_id>:d:<min>-<max>` or `:w:<min_grams>-<max_grams>`). The event then carries `shipping_rate`: service id, path, price and discounted price in the shop currency (`price_set.shop_money`), and the line's title; it's null otherwise, including with rates off, when every paid order is sent as before. `fulfillment_orders/*` skips the same orders (the query reads the order's shipping lines), so Hikyaku never gets an update for an order it doesn't have. An order sent before rates were turned on that didn't use a Hikyaku rate stops getting updates. The Orders import screen still lists and sends every importable order, without `shipping_rate`; restricting it to Hikyaku-rate orders is a possible follow-up.

**Re-routing after payment.** `app/routes/webhooks.fulfillment_orders.tsx` handles `fulfillment_orders/moved`, `split`, `merged`, `cancelled` and `scheduled_fulfillment_order_ready`. The payloads only name fulfillment orders, so the pure `app/lib/fulfillment-order-webhook.ts` picks out the ones to look the order up through (`getFulfillmentOrderOrder`, trying the next if one is gone) and the ones the change released items from (the one moved out of, split, merged or cancelled; none for scheduled-ready). The handler then sends an `order.fulfillment_updated` event: `order` `{ id, name }` only, the order's current groups from `buildFulfillmentGroups` (all of them, not just the changed ones, and sent even when empty) and `released_group_ids`. Hikyaku takes the recipient and line items from the order.paid it already has, replaces a package whose group now ships from another warehouse or weighs something else, drops the package of a released group that's no longer listed, and makes packages for new groups; a change that touches a package already loaded needs attention instead. A group that's simply gone without being released (fulfilled) keeps its package. Same 1 s Admin budget and retry contract as `orders/paid`. Known gap: an order whose every fulfillment order was `SCHEDULED` at payment never reached Hikyaku, so its scheduled-ready update is skipped there.

## Admin API usage

The app makes a small, fixed set of Admin GraphQL queries and mutations, all in `app/lib/shopify-admin.server.ts`. Get a client with `adminForRequest(request)` (embedded admin loaders/actions, via `authenticate.admin`) or `adminForShop(shop)` (webhook handlers and other work with no admin session, via `unauthenticated.admin` and the shop's offline session). Adding a query means adding its scope to `shopify.app.toml` and a line here.

| Query | Function | Scopes | Why |

| mutation `deliveryProfileUpdate` | `updateDeliveryProfile` | `write_shipping` | Static path: creates, updates and deletes the app's method definitions (and the zones it created). |
| `deliveryCustomizations` with the `$app:hikyaku` `coverage` and `rates` metafields; mutations `deliveryCustomizationCreate` / `Update` / `Delete` | `listDeliveryCustomizations`, `createDeliveryCustomization`, `updateDeliveryCustomization`, `deleteDeliveryCustomization` | `write_delivery_customizations` | Static path: turns on the Function that keeps the Hikyaku rate fitting the address and hides the rest, and gives it the coverage and rate map. |

No REST calls. The only mutations are the carrier service, delivery profile and delivery customization ones above.

**Static rates** (HIK-216; `app/lib/static-rates.server.ts`, pure parts in `static-rates.ts`). For shops whose plan can't use a carrier service. `syncStaticRates` reads hikyaku-api's static plan (`fetchStaticPlan`: one flat rate, distance bands or weight bands per service, a coverage export and a `bbox_fallback` flag), the shop's mapped locations (`warehouse` mode, not stale) and its delivery profiles, then:
- In every location group that ships from a mapped location, for each mapped location's country, writes one method definition per rate into the zone that lists the country, else the group's Rest of World zone (making a zone for a country Rest of World covers would hide the merchant's own rates there), else a new zone "Hikyaku · <CC>". Weight bands get Shopify weight conditions; distance bands are left to the Function.
- The app owns every method definition and zone whose name starts with "Hikyaku · " (`methodName`: "Hikyaku · <service>[ · <band>]") and nothing else: a resync recreates deleted ones, undoes hand edits, removes Hikyaku methods from zones that no longer qualify and deletes its own zones when unneeded. A method whose weight band changed is deleted and recreated. Nothing changed means no mutation.
- Creates or updates the "Hikyaku rates" delivery customization (Function handle `hikyaku-delivery-rates`) with two JSON metafields in `$app:hikyaku`: `coverage` (hikyaku-api's export, as is) and `rates` (`functionRates`: method name → service id, display name, kind, distance band in km). Either over 10 KB refuses the sync.
- Stores the method name → rate code map in `ShippingRates.staticRates` (for `findHikyakuShippingLine`) and any failure in `ShippingRates.error`.

`removeStaticRates` deletes the Hikyaku methods and zones, then the delivery customization (rates first, so a half-done removal never leaves rates without their filter). `removeHikyakuRates` (`shipping-rates.server.ts`) removes both paths; disconnecting Hikyaku on Home runs it. After uninstall the app has no token and Shopify keeps the method definitions, so merchants must remove rates **before uninstalling**.

**The Function** (HIK-215): `extensions/hikyaku-delivery-rates`, a JS delivery customization Function (target `cart.delivery-options.transform.run`, API `2026-07`). All its logic is the pure `decide` in `src/hikyaku-rates.ts`; the entry point only maps the input query onto it. Per delivery group, it finds the Hikyaku options by title or code in the `rates` metafield, picks the mapped warehouse nearest the address (the input has no shipping location), and:
- hides every Hikyaku option when the address has no coordinates, the warehouse doesn't cover it (`e` covered everywhere, else point-in-polygon over `p` rings or inside `b` boxes), the checkout currency isn't the rates' currency (or `presentmentCurrencyRate` isn't 1), or either metafield is missing or malformed (fail closed);
- otherwise keeps flat rates, weight bands (Shopify's conditions already filtered them) and the distance band containing the straight-line distance, one option per service (the cheaper at a shared band edge), and renames each kept option to its service name.
It never touches other options. Its tests run in the app's suite (`vitest.config.ts` includes `extensions/*/src/**/*.test.ts`). `extensions/*` are pnpm workspace packages; `shopify app function build` (run inside the extension) compiles it to `dist/function.wasm`, and `shopify app function run --input <json>` reports instructions: about 4.7M of the 11M limit with a coverage export twice the 10 KB budget.

**Resync push.** hikyaku-api POSTs `/hikyaku/resync` (`app/routes/hikyaku.resync.tsx`) when something behind a shop's static rates changes, signed with `HIKYAKU_SHOPIFY_PUSH_SECRET` (`X-Hikyaku-Timestamp` and `X-Hikyaku-Signature: sha256=<hex HMAC of "<timestamp>.<body>">`, ±5 minutes; `app/lib/hikyaku-push.server.ts`). Shops with static rates on are resynced through their offline session; anything else answers 200. A failed resync answers 500 so hikyaku-api retries.

**Which path** (HIK-217; `app/lib/rates-setup.server.ts`, pure parts in `rate-path.ts`). Shopify has no field for carrier-calculated shipping, so `capabilityFromPlan` reads `shop.plan`: Shopify Plus, Advanced, Plus (Trial), Agentic Enterprise and Development are live; Basic, Starter, Lite and Retail are static (a development store reports the plan it mirrors, so a Basic dev store is static even though Shopify would let it register a carrier service); anything else (Grow, trials) is probed. `HIKYAKU_RATES_PATH=live|static` forces a path for testing. `applyRates(admin, shop, { enabled })`:
- Live or probe: registers the carrier service switched off first. If Shopify refuses (a probe on a plan without the feature) the shop goes static, with nothing torn down. Otherwise static rates come down, then the carrier service switches on.
- Static: the carrier service comes down, hikyaku-api is told the path (it needs band settings for it; a 422 `band_settings_invalid` asks the merchant to set them), then `syncStaticRates`.
- A carrier service Shopify switched off itself (a downgrade) means static.
- hikyaku-api gets the path and shop currency whenever either changed (GET then PUT of its settings).
- A failed step leaves the shop on its old path, with the error in `ShippingRates.error`; the old path is always down before the new one goes up, so both never show at once. `ShippingRates` also records the plan and currency it set up for.
- Off removes both paths (`removeHikyakuRates`).
`reconcileRates` re-runs it for shops with rates on: on loading the Shipping rates screen, and from `shop/update` when the plan or currency changed or the last attempt failed.

**Carrier service** (`app/lib/carrier-service.server.ts`, pure parts in `carrier-service.ts`): `ensureCarrierService(admin, shop, { active })` creates the shop's one Hikyaku carrier service (name "Hikyaku", service discovery on) or reuses it, changing only what differs; `removeCarrierService` deletes it. Its GID is kept in the `ShippingRates` Prisma model, the app's record of what Hikyaku rates set up in the shop (whether rates are on, the path, GIDs, the last setup error); which services are offered lives in hikyaku-api. The callback is `HIKYAKU_API_URL` + `/api/v1/integrations/shopify/carrier-rates`, or `HIKYAKU_CARRIER_CALLBACK_URL` when set (development, where the API is on localhost). hikyaku-api verifies the callback's `X-Shopify-Hmac-Sha256` with this app's client secret. Disconnecting Hikyaku on Home removes the carrier service first (a failure is logged, not blocking), and `disconnect` deletes the `ShippingRates` row, so `app/uninstalled` and `shop/redact` clear it too; Shopify drops an uninstalled app's carrier service itself. Fulfillment order queries deliberately skip `destination`: the delivery address already arrives in `orders/paid` (or, for an earlier order, `getOrder`).

**Level 2 protected customer data.** Name/address/phone/email arrive on the `orders/paid` payload, and `read_merchant_managed_fulfillment_orders` can also read the same destination address on fulfillment orders (not queried, see above). Publishing requires Level 2 approval in the Dev Dashboard; development stores work without it.

## Webhooks

Webhooks are declarative in `shopify.app.toml` (`[[webhooks.subscriptions]]`), synced via `shopify app deploy`, not registered in code.

| Route | Topics | Status |
| --- | --- | --- |
| `webhooks.orders.paid.tsx` | `orders/paid` | Forwards the order to `hikyaku-api` with its fulfillment groups (see Order flow). |
| `webhooks.locations.tsx` | `locations/create`, `locations/update`, `locations/activate`, `locations/deactivate` | Upserts the location's name, country and street address from the payload to `PUT /api/v1/integrations/locations` without `mode`, so a new location lands `unmapped` and an existing one keeps its mapping. Skips (200) shops not connected to Hikyaku. Same retry contract as `orders/paid`: 5xx, network error or the 4 s timeout returns 500, 4xx returns 200. A 403 (the connected account lacks `integrations.locations.write`) is logged and dropped: the Home banner still counts the location from Shopify's live list, and Locations syncs everything once the account has the permission. |
| `webhooks.fulfillment_orders.tsx` | `fulfillment_orders/moved`, `fulfillment_orders/split`, `fulfillment_orders/merged`, `fulfillment_orders/cancelled`, `fulfillment_orders/scheduled_fulfillment_order_ready` | Sends the order's current routing as `order.fulfillment_updated` (see Re-routing after payment). Skips (200) shops not connected to Hikyaku. |
| `webhooks.shop.update.tsx` | `shop/update` | With Hikyaku rates on, re-checks the path (`reconcileRates`) when the plan or currency changed, or the last setup failed; any other change returns at once. 500 only when the re-check threw. |
| `webhooks.app.uninstalled.tsx`, `webhooks.app.scopes_update.tsx`, `webhooks.compliance.tsx` | App lifecycle and mandatory compliance topics | Session bookkeeping. `app/uninstalled` and compliance are HMAC-verified by `verifyWebhook` (`app/lib/webhook-verification.server.ts`, invalid → 401), not `authenticate.webhook`: with expiring offline tokens it refreshes the token first, which fails once the app is uninstalled, and answers an unlogged 500 without running the handler ([shopify-app-js#3360](https://github.com/Shopify/shopify-app-js/issues/3360), HIK-204). `app/uninstalled` deletes the shop's sessions and `HikyakuConnection`, unless `isAppInstalled` says a late retry arrived after a reinstall. `shop/redact` deletes the shop's sessions (`deleteShopSessions`), `HikyakuConnection` with its Vault secrets (`disconnect`) and leftover `HikyakuOAuthState`; location mappings live in Hikyaku, not here. `customers/data_request` and `customers/redact` answer 200: the app persists no customer data (orders are only forwarded), and the recipient details Hikyaku received are held there as the merchant's processor, so requests are handled in Hikyaku, with no propagation from this app. |

## Tests

`pnpm test` runs Vitest over `app/**/*.test.ts` (config in `vitest.config.ts`, kept apart from `vite.config.ts` so tests skip the React Router plugin). Tests cover the Function's pure logic (`extensions/hikyaku-delivery-rates/src/hikyaku-rates.ts`) and pure modules such as `app/lib/location-mapping.ts`, `app/lib/fulfillment-groups.ts`, `app/lib/fulfillment-order-webhook.ts` and `app/lib/order-import.ts`. Route tests live in `app/tests/` (anything under `app/routes/` becomes a route) and mock `shopify.server`, `hikyaku-api.server` and `shopify-admin.server`; so far `orders/paid`, `fulfillment_orders/*`, `app/uninstalled` and compliance have one, `app/tests/order-import.test.ts` covers `importOrders`, `app/tests/marketing-redirects.test.ts` covers `/` and `/auth/login` (see Outside the admin), and `app/tests/vault-session-storage.test.ts` covers the session store over an in-memory table and Vault.
